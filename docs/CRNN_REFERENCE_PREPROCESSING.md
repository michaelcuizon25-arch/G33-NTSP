# Reference-compatible CRNN preprocessing option

Implemented on `experiment/epoch3-reference-preprocessing`, based on diagnostic
commit `26f09e9`. The bundled Epoch 3 weights, model input contract, decoder, CCL,
physical-line segmentation, rule engine and app UI are unchanged. No training or
model inference was run for these comparisons.

## Selection and fallback

Existing `CrnnLineRecognizer(context)` callers continue to use `LEGACY`.
For an explicit experiment, construct:

```kotlin
CrnnLineRecognizer(context, CrnnPreprocessingMode.SIMPLE_HTR_REFERENCE)
```

`SimpleHtrReferencePreprocessor` can be tested independently of TFLite through its
bitmap entry point or `preprocessGrayscale(width, height, rowMajorGrayBytes)`.
`CrnnPreprocessing.prepare` selects the option and returns the requested/actual
mode, reference width, and fallback reason alongside the buffer. Per-line
diagnostic JSON records those values, so mixed-mode scans are distinguishable.
No production call site is switched to the new option by this change.

When the dynamic reference width exceeds 512, its result has no model input;
the selector runs the unchanged legacy transform and records
`reference_width_exceeds_512`. This is deliberately reported as a fallback,
not as reference parity. The notebook skips such lines. The option neither
truncates writing nor changes the fixed-width model.

## Supplied notebook and preprocessor semantics

Notebook JSON cell 21 uses `Preprocessor((256,32), dynamic_width=True,
padding=16, line_mode=False, data_augmentation=False)`. Its `process_img` does:

1. Convert grayscale samples to float64.
2. Set `f = 32 / originalHeight` and `wt = int(f * originalWidth + 16)`.
3. Round `wt` upwards to a multiple of four.
4. Set `tx = (wt - originalWidth * f) / 2`, `ty = 0` and a float32 affine matrix.
5. Warp onto a white 32-by-wt float64 canvas with OpenCV's default linear
   interpolation and `BORDER_TRANSPARENT`.
6. Transpose to width-major order and normalize `gray / 255 - 0.5`.
7. Cast to float32. Notebook cell 74 right-pads with +0.5 to width 512 for the
   fixed model, skipping wider lines.

The nominal 256 in `img_size` is not a cap when dynamic width is enabled. The
comment claiming [-1,1] in the Python file is inaccurate; the actual range for
ordinary input is [-0.5,+0.5].

Cells 32–33 additionally apply label-dependent horizontal stretching to some
training samples for CTC safety and batch-pad to the largest width. Labels are
unknown during inference, so that training-only step is not reproduced here.

| Property | Unchanged legacy | New reference option |
| --- | --- | --- |
| Scale | min(512/w,32/h) | 32/h |
| Width | Rounded resized image width | Truncated scaled width +16, rounded to multiple of 4 |
| Placement | Top-left, right/bottom white padding | Centered horizontal margin, then right padding to 512 |
| Interpolation | Filtered Android bitmap resize | OpenCV-compatible affine pixel grid and linear weights |
| Intermediate values | Quantized bitmap pixels | Floating interpolation, normalization in double, then float32 |
| Grayscale | Canvas desaturation | Grayscale samples or unprofiled PNG-compatible BT.601 RGB conversion |
| Long line | Shrink both axes | Explicit incompatibility; selector falls back to legacy |
| Normalization | gray/255−0.5 | Same |
| Tensor | Native-endian FLOAT32, x-major, [1,512,32] | Same |

The Kotlin affine sampler reproduces OpenCV's float32 matrix conversion,
double-precision inverse, 10-bit affine coordinate rounding and 5-bit linear
fractions. Transparent-border pixels remain white for out-of-bounds origins;
right/bottom-edge samples normalize the available weights. Interpolated values
are not rounded back to 8-bit before normalization. No OpenCV Android dependency
was added.

## Independent Python oracle and identical-crop comparison

Goldens were generated by executing only `process_img` from the supplied Python
file, not any notebook or training cells. Oracle: OpenCV **4.12.0**, numpy
**2.2.6**. The notebook does not establish its original OpenCV version, so these
are explicit comparison versions rather than an asserted original runtime.

Supplied preprocessor SHA-256:
`94e308f7142902e61937515f8726716a65418b1248f531428f7fcb121afc6f9f`.

All six independent golden cases match exactly at every float32 element:
5×80 narrow, 200×40 color, 137×43 fractional scaling, 496×32 exact-width,
1×1 single-pixel and 87×51 fractional color. The tests also verify white margins,
ink polarity, x-major placement, buffer shape/order, default behavior, fallback,
and diagnostic mode metadata.

Using the existing `board_test_5.jpg` fixture, unchanged preprocessing/CCL/physical
splitting produced 11 crops. Both transforms consume the identical bitmap for
each comparison; a PNG snapshot is made from its decoded pixel values.

- **10** crops fit the reference input. The Kotlin reference tensors match
  Python **exactly**, with RMSE and maximum absolute difference **0**.
- Legacy-versus-Python RMSE ranges from **0.06582 to 0.11486** on those same
  decoded pixels. The 753×74 title crop has dynamic width **344** and legacy RMSE
  **0.11017**, compared with **0** for the new option.
- One 1558×64 crop needs dynamic width **796**. Its selected output is
  byte-identical to legacy, with an explicit fallback reason.

An important additional difference is **file grayscale decoding**. Android PNG
compression adds sRGB metadata; OpenCV/libpng can use it for gamma-aware grayscale
conversion. Reading those PNGs directly with `IMREAD_GRAYSCALE` gives residual
reference-option RMSE **0.00089–0.00355**, maximum absolute difference up to
**0.01308**. Removing the metadata effect by re-encoding the exact decoded RGB
pixels with OpenCV's unprofiled PNG encoder produces the exact matches above.
Both reports are preserved in `crnn-reference-comparison.json` (identical pixels)
and `crnn-reference-file-decoding.json` (original PNG grayscale decoding).

This separates transform parity from image-decoder behavior. A decoded Android
bitmap cannot recover the original JPEG decoder's luminance plane or discarded
color-profile metadata. For authoritative interpolation parity, supply identical
grayscale samples through `preprocessGrayscale`. Colored headings are covered by
the unprofiled PNG oracle, but complete camera/JPEG decode parity is not claimed.

## Reproducing the comparison

Run the native-graphics `SimpleHtrReferencePreprocessorTest`. It writes both
Android options to `app/build/crnn-reference-comparison`, without model inference.

```sh
python tools/compare_crnn_preprocessing.py app/build/crnn-reference-comparison \
  --preprocessor /path/to/supplied/preprocessor.py \
  --grayscale-mode unprofiled_rgb_png --output /path/to/pixel-comparison
```

Omit `--grayscale-mode` to retain the notebook's direct grayscale-file decode and
measure its difference separately. Existing diagnostic comparison behavior
defaults to this original file mode.

Regenerate the committed independent oracle resources with:

```sh
python tools/generate_crnn_reference_goldens.py \
  --preprocessor /path/to/supplied/preprocessor.py \
  --output app/src/test/resources/crnn_reference
```

The Python tools require numpy/OpenCV in the external test environment, not new
Android dependencies. Use only a trusted supplied preprocessor module.

## Accuracy and remaining work

Validation: Android `assembleDebug` succeeded, and all **34 custom-pipeline
tests** passed (including five new tests). The full suite ran **35 tests**:
34 passed and the unchanged `MlKitRecognitionPipelineTest` failed because
`MlKitContext` was not initialized. Only the separate scratch Gradle init script
excludes that test for the custom-pipeline run; no repository test is disabled.
The existing diagnostic tests continue to verify legacy-versus-original byte
parity and nonfatal diagnostic failures.

These results establish numerical preprocessing compatibility. They do not
establish lower CER/WER or corrected spelling on the phone. That requires complete,
manually labeled physical-line crops, the same unchanged model and runtime,
legacy/reference input pairs and raw predictions. Over-wide fallbacks must be
counted separately rather than excluded silently. CCL fragments and model error
rate remain independent limitations.

Changed production files: new `SimpleHtrReferencePreprocessor.kt` and
`CrnnPreprocessing.kt`; updated `CrnnLineRecognizer.kt` for explicit selection and
`CrnnDiagnostics.kt` for per-line mode/fallback metadata. Added
`SimpleHtrReferencePreprocessorTest.kt`, six Python-generated input/tensor pairs
and their manifest. Updated the comparison tool, added the golden generator,
this document and two numerical reports. The original `CrnnInputPreprocessor.kt`
and the model assets have no changes relative to `26f09e9`.
